# Phase 2 — Auth & Identity Design

**Project:** publicserve  
**Date:** 2026-04-28  
**Status:** Approved

## Overview

Authentication via next-auth Email provider (magic link over SMTP). Sessions persisted in Azure Table Storage via a custom adapter built directly on `@azure/data-tables`. App identity (users, groups, orgs, permissions) stored in separate app-owned tables in the same storage account.

## Decisions

| Decision | Choice | Rationale |
|---|---|---|
| Auth provider | next-auth Email (magic link) | No passwords, SMTP-supplied by operator |
| Session strategy | Database sessions (not JWT) | Required by Email provider; sessions persisted in Azure Table Storage (`Sessions` table). Configured via `session: { strategy: "database" }` in next-auth config. |
| Adapter | Custom, using `@azure/data-tables` SDK directly | Explicit requirement; no pre-built Azure Tables adapter dependency |
| Table separation | next-auth tables vs app tables | Clean upgrade boundary; adapter schema stable |
| Registration | Self-registration (any email) | Open access |
| First admin | First registered user auto-elevated | No manual seed step needed |
| Permissions | Per group-org assignment (flags) | Groups are the unit of access control |

## Auth Flow

```
1. User submits email → next-auth sends magic link via SMTP
2. User clicks link → next-auth verifies token from VerificationTokens table
3. If new user: createUser callback fires → user written to Users table
   - If Users table was empty before this write → add user to admin group (UserGroups upsert)
4. Session written to Sessions table
5. httpOnly cookie set with session token
6. On each request: session token looked up → userId resolved → groups loaded from UserGroups
```

## Permission Resolution

Resolved in Next.js middleware on each request:

```
1. Read session cookie → look up sessionToken in Sessions table → get userId
2. Scan UserGroups[PK=userId] → set of groupIds (G)
3. Load Groups for each groupId in G
4. If any group has isAdmin=true → grant full access, skip steps 5–6
5. For org-scoped routes: scan OrgGroups[PK=orgId] → rows where RowKey ∈ G
6. Union the permission flags across matching rows → effective permissions for request
```

Effective permissions are attached to the request context. Route handlers and server actions check the relevant flag.

## Admin Group Behaviour

- Admin group members bypass all org-scoped permission checks
- Admins can: create/delete orgs, create/delete groups, assign groups to orgs, manage any user, configure any storage location
- `isAdmin` flag on Groups table is the single source of truth — multiple admin groups are permitted

## SMTP Configuration

SMTP credentials stored as Key Vault secrets:

| Secret name | Description |
|---|---|
| `smtp-host` | SMTP server hostname |
| `smtp-port` | SMTP server port |
| `smtp-user` | SMTP username |
| `smtp-password` | SMTP password |
| `smtp-from` | From address for magic link emails |

Loaded at runtime via Key Vault reference (SWA managed identity → Key Vault Secrets User).
